# zcash/consensus/gaps/ed25519: Ed25519 with Zcash's rules (ZIP 215) in Bend

This directory holds an Ed25519 signature verifier for Sprout `joinSplitSig`, written in Bend 2
(the forked compiler, `U32.mac64`). Zebra checks joinSplitSig with the rules of
**ed25519-zebra 4.2.0** (`VerificationKey::try_from(A)?.verify(&sig, msg)`), and this module
implements exactly those rules. It is differentially tested against that crate. No Rust is
linked into the Bend side; Rust is only the oracle (`oracle/`).

```
import ed25519.bend as Ed        # from zcash/consensus/gaps/sprout/
Ed.verify(pk: +List<U32>, sig: +List<U32>, msg: +List<U32>) -> Bool
```

Each byte is one U32 (0..255), as in `zcash/sapling/tx/stx.bend`. `pk` is the 32-byte encoding of A,
`sig` is the 64-byte R || S, and `msg` is the signed bytes. For joinSplitSig, `msg` is the
32-byte SIGHASH (dataToBeSigned). If pk is shorter than 32 bytes or sig is shorter than 64,
the signature is rejected. Bytes beyond 32 / 64 are ignored, so pass exact fields.

## Rules implemented (ed25519-zebra 4.2.0 + curve25519-dalek 4.1.3)

1. **S canonical**: S (sig[32..64], little-endian) must be < ℓ = 2^252 + 27742317777372353535851937790883648493, or the signature is rejected (`Scalar::from_canonical_bytes`).
2. **A and R decoding** (`CompressedEdwardsY::decompress`):
   - y is the low 255 bits, taken mod p. Non-canonical y ≥ p is accepted.
   - u = y² − 1 and v = d·y² + 1.
   - `sqrt_ratio_i` is computed exactly as dalek does it: r = (uv³)(uv⁷)^((p−5)/8) and check = v·r². The point is valid iff check = u or check = −u. r is multiplied by √−1 if check = −u or check = −u·√−1. Then r is made nonnegative (even canonical value), and x = −r if bit 255 is set.
   - "Negative zero" (x = 0 with the sign bit set) is accepted.
   - Small-order and mixed-order points are accepted.
   - A point is rejected only when no square root exists.
3. **k** = SHA-512(R_bytes ‖ A_bytes ‖ M) mod ℓ, computed over the bytes **as given**, not over re-encoded points (`Scalar::from_hash`: the digest is read as a little-endian 512-bit number).
4. **Cofactored equation**: accept iff [8]([s]B − [k]A − R) is the identity. Identity here means X = 0 and Y = Z in extended coordinates.

The order of checks is S, then A, then R, then the equation. Every failure gives the same
verdict (false), as in Rust.

| File | What |
|---|---|
| `ed25519.bend` | `verify`, decoding, the curve formulas (extended coordinates, HWCD a = −1 doubling and mixed Niels addition, complete on edwards25519), a joint double-and-add for [s]B + [k](−A), and k mod ℓ |

Record format, shared by `ed_main` and the oracle: u32 count, then for each record
pk 32 | sig 64 | msg_len u32 | msg, all little-endian.

**Field note.** The groth16 generator asserts that p's top limb is < 2^63−1. For 2^255−19 the
top limb is exactly 2^63−1. The merged (no-carry) CIOS is still exact here, for this reason:
when the operand multiplied word by word is < p, every iteration keeps t < 2p < 2^256, so the
final carry word never overflows. `from_raw` therefore puts R² on that side, which lets it
accept any raw value < 2^256 (for y ≥ p and the 256-bit hash halves). The generator asserts
p < R/2, and the claim is checked by `t/field_test.py`, including the edge values p−1, p,
2p−1, 2^255−1, 2^256−1, ℓ±1, and others.

- **Non-canonical encodings accepted when the equation holds.** Of the 26 non-canonical
  encodings, the only points whose discrete log is known are the 6 small-order ones. So the
  accepted non-canonical cases are: nc_A 24, nc_R 24, nc_AR 12, and the zip215 set. The other
  20 encodings are large-order points with no known discrete log. Those are exercised as
  rejects, and their decoding is checked directly (below).
- **Cofactorless fails, cofactored holds.** The oracle also evaluates the cofactorless equation
  [s]B = R + [k]A. Among the Rust-valid records, it fails for all 400 mixed_R and 319 / 334 of
  mixed_A / mixed_AR (the rest have [k]T = 0). It also fails for 157 of the 196 zip215 cases
  and for 92 of the small-order / non-canonical cases in `main`. Bend accepts all of them, as ed25519-zebra does.

## Speed

`ed_main data/bench_valid.bin +RTS --threads 1`: 10,000 honest signatures with 32-byte
messages, on an M5 Max. Other agents' jobs kept the load average between 26 and 31, so these
figures are noisy.

| | per verify |
|---|---|
| **Bend, 1 thread** (6 runs) | **111–149 µs** |
| Bend, 18 threads | ~11 µs |
| Rust ed25519-zebra 4.2.0 `verify`, 1 thread, same records | 31–35 µs |

Bend is about 3.5–4× slower than Rust. That is far inside the 50 ms budget: a few hundred
signatures take well under 0.1 s on one thread. Building `ed_main` takes about 5 s and fits
the default heavy.sh memory limits.

## Rebuild / rerun


The script regenerates the Bend modules, builds the oracle and the three Bend programs (all
under `heavy.sh`), and reruns every test above, ending with the speed comparison. Single steps:

- `../../../../tools/heavy.sh ./build.sh ed_main.bend ed_main`
- `oracle/target/release/ed25519-oracle gen data/X SEED NVALID`
- `./ed_main data/X.bin > data/X.bend.out`
- `python3 diff.py data/X.meta data/X.bend.out`

`data/` (about 66 MB, mostly layer dumps) can be deleted and regenerated.

## Honest limitations

- **Arithmetic is variable-time.** That is fine for verification, where all data is public. Do
  not reuse this field code for secrets.
- **The scalar multiplication is plain.** It is a joint double-and-add with 256 doublings and
  no windows, no precomputed B table, and no batch verification. That accounts for most of the
  gap to Rust; a 4-bit window or a fixed-base table would roughly halve the time if it ever
  matters.
- **Coverage of non-canonical, large-order points is limited to decoding and rejects.** A
  *valid* signature on one of those 20 points cannot be built without its discrete log, so
  none was tested. Their decoding equals dalek's, the equation code is the same for every
  point, and mixed-order acceptance is tested separately.
- **No real mainnet joinSplitSig data has been run through the module yet.** That will happen
  through the Sprout checker during integration. All tests here use generated vectors, judged
  by ed25519-zebra 4.2.0.
- **Message length**: lengths are counted in a U32 and the SHA-512 padding encodes length < 2^29 bytes, far beyond any transaction.
