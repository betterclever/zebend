# decomp: table-based square roots and faster point decompression

Drop-in square roots for field3's `fp64`/`fq64` and point decompression for Pallas/Vesta,
then the same change applied to copies of the Halo 2 batch verifier (`v64/`, from
`perf3/v64`) and the RedPallas signature batch (`sig/`, from `sigbatch`). `perf3/` and
`sigbatch/` themselves are untouched. Everything is measured against the same sources built
with the same compiler (forked Bend `u64-rot`, `build.sh`).

**Results (M5 Max; load average 4–9 from other jobs).** Square root 80 → 59 ms per 10⁴
(Rust pasta_curves 42 ms); decompression 81 → 59 ms per 10⁴ attempts (Rust 42 ms). Both
match pasta_curves exactly on 2,097,152 inputs per field plus 103 edge cases per field.
Signatures, 1 thread: **+27%** (17.2k → 22.0k sigs/s; Rust 24.5k). Halo 2, 1 thread:
**+4–5%** (122 → 128 bundles/s). The 18-thread runs were too noisy to show a difference.
All verdicts are unchanged.

## Algorithm

pasta_curves' `sqrt-table` (Sarkar, eprint 2020/1407): for p − 1 = t·2³², compute
v = u^((t−1)/2) with pasta's addition chain (about 224 squarings, using field3's dedicated
squaring), then y = u·v² = u^t lies in the 2³²-th roots of unity. Its discrete log to
w = 5^t comes from 8 table lookups instead of Tonelli–Shanks' up-to-32 rounds of repeated
squaring, and the root is u·v·w^(e/2).

Two differences from pasta:

- **4-bit windows, not 8.** The forked compiler needs ~0.6 MB per `match` arm (it was
  measured: 2,048 arms ≈ 1.2–1.5 GB whatever the table shape). pasta's 8-bit tables would be
  ~8,200 limb arms per field, ~4 GB on top of the Halo 2 build (already 2.5 GB in bun). With 4 bits it is ~1,100 arms. The cost is
  28 extra multiplications per root (38 instead of ~14 after the chain).
- **Hash on the Montgomery limb.** The discrete log in the 16th roots of unity hashes the
  low 32-bit Montgomery limb, `(l0 · M) >> 26`, into 64 slots packed four to a word. pasta
  reduces first and uses a xor/mod hash.

Every table is a dense `match` on U32 literals returning one limb, which the compiler turns
into a constant array (`TAB_AT`). So `root` has no data-dependent branches and does the same
work for every input. That makes it the GPU variant too (`decompress_ct`). Table lookups
indexed by secret data are still cache-observable on a CPU. Only public data (proof points,
R, rk, cv) goes through these functions.

Decompression-level changes:
- **Early rejection.** A non-canonical x costs one comparison and no square root (as before).
- **Constant points.** sigbatch decompressed V (once per chunk) and both bases (once per
  batch equation and bisection step). They are now affine constants. The effect is not
  measurable: a constants-only build matched the base build, 9.46 vs 9.46 s on 20 chunks.
  The Halo 2 verifying key was already affine constants.
- **Batch inversion before affine conversion.** Not needed on either path. Halo 2 already
  skips the inversion for decompressed points (z = 1, `vlib.aff_fast`). In sigbatch, the
  only per-signature inversion is the binding bvk encoding (303,047 signatures, ~6 µs each,
  ~2% of 1-thread time). That one was not batched.

## Speed

M5 Max. `micro_bench.sh`: 5 interleaved rounds, medians, load average 6–7.

| 1 thread, per 10⁴ | field3 | **decomp** | Rust pasta_curves 0.5 |
|---|---|---|---|
| Fq sqrt (x += i) | 80–84 ms | **59–60 ms** | 41–42 ms |
| Fp sqrt | 80–82 ms | **58–60 ms** | 42–43 ms |
| Vesta decompress attempts (x = 7 + i) | 81–83 ms | **58–61 ms** (`decompress_ct` 58–60) | 42–43 ms |
| Pallas decompress attempts | 80–87 ms | **58–60 ms** | 42–43 ms |

GPU (`gpu_dec`, 131,072 Vesta decompressions; `gpu_gate.sh`, 20 runs; min/median/max):

| | field3 | table | table, fixed work |
|---|---|---|---|
| Metal | 97/99/106 ms | 87/90/92 ms | 88/92/95 ms |
| CPU 18 threads | 72 ms | 54 ms | 56 ms |
| CPU 1 thread | 1,054 ms | 775 ms | 777 ms |

On Metal the table root is ~9% faster than field3's. It still loses to 18 CPU threads. The
fixed-work variant does not beat the variable-time one on Metal, so lane divergence is not
what limits it.

**Halo 2 batch** (`h2_check.sh`; 10,048 bundles in 157 processes of 64; base and new
alternate; load average 7–9):

| | base (perf3/v64) | **decomp/v64** | Rust halo2 `BatchVerifier`, same session |
|---|---|---|---|
| 1 thread | 125 / 122 / 116 bundles/s | **132 / 128 / 121** (paired +4–6%) | 55 |
| 18 threads | 519 / 701 / 731 | 667 / 651 / 672 (no difference within noise) | 757 |

Decompression is a small part of a Halo 2 proof's verification (one square root per
commitment, against MSMs over thousands of points), so ~5% is the expected order. The Rust
1-thread figure (55/s) is lower than proofsets' earlier 94/s; the machine was shared.

**Signatures** (all 1,283,411 in 157 processes; `sig_check.sh`, plus the paired `sig_1t.sh`
on chunks 0–39, which alternates base and new per chunk, 3 passes):

| | base (sigbatch) | **decomp/sig** | Rust reddsa batch, same session |
|---|---|---|---|
| 1 thread, paired (327,480 sigs) | 16.4k / 17.2k / 17.3k sigs/s (prep 12.9 s) | **20.5k / 21.8k / 22.1k** (prep 8.8 s) | — |
| 1 thread, all chunks | 13.8k | 19.9k | 24.5k |
| 18 threads, all chunks | 129k / 92k | 142k / 114k | 303k |

Preparation is 32% faster and the equation is unchanged, so 1-thread throughput rises 27%.
That is ~12.7 µs saved per signature: more than 2.5 decompressions × the 2.2 µs that the
microbenchmark predicts. field3's variable-time Tonelli–Shanks may cost more on these
inputs; this was not investigated. The 18-thread runs drift with load (base 129k then 92k),
so they show the direction, not the size.

## Integrating into perf3/v64 and sigbatch

Nothing in `perf3/` or `sigbatch/` was changed. To adopt:

**perf3/v64 (Halo 2):**
1. `perf3/v64/vlib.bend`: add `import ../../decomp/vesta_dec.bend as VD` after the other
   imports, and in `rd_point_go` replace `V.decompress(w)` with `VD.decompress(w)` (the only
   call site; `bundle_ba`, `batch_main`, `loop_ba` all go through it). This is exactly the diff
   between `decomp/v64/vlib.bend` and `perf3/v64/vlib.bend` apart from import paths.
2. Rebuild with `perf3/build.sh` (or `decomp/build.sh`). Compile memory rises by roughly
   0.7 GB; the Halo 2 batch build peaked at 4.7 GB RSS under `/usr/bin/time`.
3. Optional: `python3 decomp/v64/gen_variants.py` writes `bundle_ba_nu62/prenu62` on v64.
   It works only on the copy in `decomp/v64` (paths are relative to it).
4. Check: `run_bundles.py` on the three sets, then `h2_check.sh` (adjust `v64/` paths).

**sigbatch:**
1. `sigbatch/sig.bend`: add `import ../decomp/pallas_dec.bend as PD`, and replace
   `P.decompress(` with `PD.decompress(` in `cv_go`, `vk_sel` and `pr_s` (3 call sites).
2. Optional (no measurable gain): replace `vpt`, `base_sa`, `base_bd` with the affine
   constants from `decomp/sig/sig.bend` (needs `import ../field3/fp64.bend as Fp`).
3. Rebuild with `sigbatch/build.sh`; check with `decomp/sig_check.sh` (tamper indices and
   prep digests) pointed at the new binary.

`batch_gpu` picks the change up through `sig.bend` too. It was not rebuilt or measured on
Metal here.

## Not done

- 8-bit tables (pasta's layout): ~4 GB more compiler memory per field, and the expected gain
  is about 0.5 µs per root.
- Batching the bvk-encoding inversions in sigbatch (~2% of 1-thread time).
- Metal runs of the integrated Halo 2 / signature programs. Only `gpu_dec` was measured and
  gated on Metal.
